## 1. 结论先行

### 1.1 交付物是 0

用交付物口径（不是代理指标）量出来的漏斗，四个 benchmark：

| 阶段 | 数量 | 转化 |
|---|---|---|

**B = 0。** 这是项目的名字所承诺的东西（Verifier-derived **P**arameterized **U**nit
**T**ests），五天之后它是零。而且 0 的原因不是"难"，是 **emitter 的数据结构里根本没有
"区间"和"断言"这两个概念**，加上**认证在发出之后运行**——两端在时间上是反的。

### 1.2 那 7 个"认证成功"里有 6 个是假的

工具自己的 applicability metric 写着：

> "A coordinate certified as `[v, v]` is a concrete test with extra syntax."

farming 的 3 条认证路径，**坐标 100 % 是单点 `[v,v]`**。整个语料里真正有宽度的坐标
只有 **12 个，全部在 aqua 一个 benchmark 上**。

所以 subgoal 3（完美实现区间输入）的真实状态不是「4 % 已认证」，而是
**171 条见证 → 12 个真正的区间，集中在一个合约上**。

### 1.3 而 st1inch 的 0/86 有一个我五天没说出口的解释

下一节。**它不是"求解器解不动 256 位算术"，是"构造器的守卫污染了每一条路径条件"。**
这个区别决定了修法完全不同，而且后者是可修的。

## 2. 那 3 行函数，逐层拆开

### 2.1 函数本身

```solidity
function setFeeReceiver(address feeReceiver_) public onlyOwner {
    if (feeReceiver_ == address(0)) revert ZeroAddress();
    feeReceiver = feeReceiver_;
    emit FeeReceiverSet(feeReceiver_);
}
```

一个权限检查、一个零地址检查、一次赋值、一个事件。任何人手写测试要 5 分钟：

```solidity
function test_setFeeReceiver_zero_reverts() public {
    vm.prank(owner);
    vm.expectRevert(ZeroAddress.selector);
    st.setFeeReceiver(address(0));
}
```

### 2.2 我们的工具在它上面的实际表现

| 度量 | 值 |
|---|---|
| 枚举出的完整路径 | 5 |
| 见证（拿到反例）的 | **0** |
| VCC | 10（因为构造器也调用它，D33） |
| symex | 0.098 s，1526 条赋值 |
| VCC 化简后 | 875 条赋值 |
| **编码成 SMT** | **0.028 s** |
| **求解** | **z3 `out of memory` / bitwuzla 120 s 不返回 / cvc5 `std::bad_alloc`** |

**编码只要 28 毫秒，求解耗尽 8 GiB。** 公式很小，但极难。

### 2.3 这条路径的路径条件，本身有多难？

`setFeeReceiver:path:2`（最短的那条，msg.value 非零 → 回滚）的决策序列是：

```
line 2233  msg.value == 0        (合成的 ABI 值门)
```

一条约束。`path:15`（正常退出）是三条：

```
msg.value == 0
msg.sender == owner            (onlyOwner)
feeReceiver_ != address(0)
```

**三条线性约束，256 位。任何 SMT 求解器在微秒级解掉。** 一个 fuzzer 随机撒点，
第一发就能命中前两条。

### 2.4 那么 8 GiB 花在哪了？

花在**这条路径条件之外的东西**上。我们交给求解器的公式里，除了上面三条，还有：

**(a) 整个构造器的符号执行**，包括：

```solidity
constructor(IERC20 oneInch_, uint256 expBase_, address feeReceiver_)
    ... VotingPowerCalculator(expBase_, block.timestamp) ... {
    if (_votingPowerAt(1e18, block.timestamp + MAX_LOCK_PERIOD) * 20 < 1e18)
        revert ExpBaseTooBig();
    if (_votingPowerAt(1e18, block.timestamp + MAX_LOCK_PERIOD + 1) * 20 > 1e18)
        revert ExpBaseTooSmall();
    setFeeReceiver(feeReceiver_);
    ONE_INCH = oneInch_;
}
```

而 `_votingPowerAt` 是 **30 个独立分支，每个分支一次 256 位乘法和一次 256 位除法**：

```solidity
if (t & 0x1  != 0) { v = (v * T0)  / 1e18; }
if (t & 0x2  != 0) { v = (v * T1)  / 1e18; }
...  // 30 层
```

**它被调用了两次，结果被比较，不满足就 revert。**

**(b) ERC20 的 name/symbol 字符串赋值**（`nondet_string` / `_str_assign` 三个循环，
每次运行都被截断警告点名）。

**(c) 外部调用重入模型**（把外部调用建模成对本合约 dispatcher 的 nondet 重入）。

**(d) dispatcher 本身。**

### 2.5 ⛔ 关键：构造器的 revert 守卫，是每一条单元路径的隐含前提

这是我五天没说出口的那一句。

我们的 harness 把「部署 + N 笔交易」建模成**一个符号程序**。单元路径的可行性
（"存在输入走这条路"）因此隐含地断言了 **"部署没有回滚"**。而对 st1inch，
"部署没有回滚" 展开就是：

```
_votingPowerAt(1e18, T) * 20 >= 1e18   ∧   _votingPowerAt(1e18, T+1) * 20 <= 1e18
```

即**两次 30 层条件化 256 位乘除的联立**。

⇒ **所以 `setFeeReceiver` 那三条平凡约束，是和这个东西合取在一起交给求解器的。**

⇒ **所以合约里的每一个单元都解不动**，不管那个单元本身多简单。86 条决策全部拿不到，
不是 86 个难题，**是同一个难题被复制了 86 次**。

### 2.6 我自己的数据早就证明了这一点，而我给了另一个解释

D36 的阶梯（每一级只加一个成分）测量结果：

| 级 | F | 判定 |
|---|---|---|
| 函数本身（owner、modifier、error、event） | **4/4** | ✅ 0.002–0.004 s |
| + 构造器调用该单元 | **4/4** | ✅ |
| + 30 个 immutable `T_k = (T_{k-1}²)/1e18`（直线） | **4/4** | ✅ |
| + name/symbol 字符串 | **4/4** | ✅ |
| **+ 构造器调用 30 分支的 `_votingPowerAt`** | **0/4** | ⛔ |

**只有最后一级翻转。** 我当时写下的结论是：

> 「条件化的宽位宽算术。30 层在 64 位是平凡的，128 位超过 120 秒预算，256 位 z3
> 几秒内内存耗尽。」

**这个结论是对现象的正确描述，但它把因果放错了层次。** 正确的说法是：

> **构造器里有一个求解器算不动的 revert 守卫，而我们的建模让这个守卫成为
> 合约内每一条单元路径的合取项。**

前一种说法指向的修法是「换后端 / 提高预算 / 优化编码」——**我为此花了 D31、D37、
D38 三份文档和一次 900 秒的 cvc5 重跑，全部失败。**

后一种说法指向的修法是「**别去解构造器，去执行它**」——**我一次都没试过。**

## 3. 本质错误：我们在"求解"一件本该"执行"的事

### 3.1 一句话

**构造器一旦参数确定，就没有任何不确定性——它是一段确定性代码，跑一遍就知道结果。
我们却把它编码成约束，交给 SMT 求解器去证明它不回滚。**

`_votingPowerAt(1e18, T) * 20 >= 1e18` 这个式子，在 `expBase_` 和
`block.timestamp` 都是具体值的时候，是一个**闭公式**——它要么真要么假，用 30 次
整数乘除算出来，**微秒级**。只有当 `expBase_` 是符号量的时候，它才是那个让 z3 耗尽
8 GiB 的东西。

而**测试根本不需要 `expBase_` 是符号量**。发出的测试里必须写一个具体的部署：

```solidity
st = new St1inch(token, EXP_BASE, feeReceiver);   // 全部具体值
```

**我们为了发出一个具体部署，先去符号地求解了所有可能的部署。**

### 3.2 这就是单元测试和整程序验证的分界，而我站错了边

| | 整程序验证 | 单元测试生成 |
|---|---|---|
| 部署 | 符号的：对所有合法构造参数成立 | **具体的：一个部署** |
| 入口状态 | 所有可达状态 | **一个确定的后置状态** |
| 交付物 | 性质的证明 | **一条能跑绿的用例** |

我们的**问题定义**站在右边（用户裁定过：单元是外部可调用的入口点，路径是一次调用，
路径域是**测试能给出的输入**）。而我们的**求解任务**站在左边。

**这两边不一致，就是这五天的根本病灶。** 它同时解释了三件我一直分开处理的事：

1. **st1inch 0/86** —— 构造器守卫污染每条路径条件（§2.5）。
2. **`bounded-holds` 占了未见证路径的 100 %（751 条）** —— 入口状态从不 havoc、
   是后构造状态，所以需要"前一笔交易建立的状态"的路径全部落进这个桶。而如果部署是
   具体的、状态是具体的，那么该 havoc 的是**状态变量**，不是整个部署过程。
   我一直把它当"要不要 havoc 入口状态"的开关问题，它其实是"入口状态该由谁决定"的
   建模问题。
3. **`I`（证明不可达）结构性为 0** —— `path_cov_can_prove_unreachable()` 无条件
   返回 false。我记录了这个事实五天，也记录了"不能直接翻这个布尔"，但没意识到：
   在**具体部署 + 具体入口状态**下，"这条路径不可达"是一个**可判定**的问题，
   `I` 本来是可以有意义的。

### 3.3 为什么我没想到

诚实地说：因为我一直在**修工具报告的准确性**，而不是在**质疑工具解题的方式**。

五天里我做了大量这种工作：U-reason 归类是否正确、报告是否标记 partial、语料是否跨
构建、陈旧文件是否被误算、31 条缺失决策是否逐条归因。**这些全是"我们的度量是否
诚实"的问题。** 它们有价值——一份不诚实的度量会让所有后续判断失效——但它们
**一条都不会让那 3 行函数产出一个测试**。

我把"审计"当成了"进展"。

## 4. 诚实回答：为什么 fuzz 更容易

用户说「我要是插个桩自己去 fuzz 都不会有这么吃力」。**这句话是对的，而且我应该
能说清楚它为什么对，以及我们凭什么还值得存在。**

### 4.1 fuzz 在这件事上强在哪

| | fuzz | 我们 |
|---|---|---|
| 部署 | **具体执行**，微秒 | 符号求解，8 GiB 耗尽 |
| 找到 `msg.sender == owner` | 直接用 `vm.prank(owner)`，零成本 | 一条 SMT 约束，混在构造器守卫里 |
| 找到 `feeReceiver_ != 0` | 随机撒点，第一发命中概率 ≈ 1 | 同上 |
| 覆盖 3 行函数的 2 条分支 | **秒级** | **900 秒不返回** |
| 需要的工具 | forge fuzz，已内置 | 一个 156 KB 的 emitter + 四阶段流水线 |

**在"让简单函数的简单分支被执行到"这件事上，fuzz 完胜，而且不是一点点。**
这不是我该辩解的地方。

### 4.2 那我们凭什么还值得做

只有三件事 fuzz 做不到，而且**只有第三件是我们承诺过的**：

1. **穷尽性**：fuzz 不知道自己漏了什么。我们枚举完整路径，能说"这个单元有 5 条路径"
   并对每一条给出状态（F/U/I）和**理由**。——这一条我们做到了，而且做得不错
   （31/31 缺失决策逐条归因）。
2. **不可达的判定**：fuzz 撒不到的路径和不存在的路径，它分不开。我们**本来**能分，
   但 `I` 结构性为 0，所以**目前也分不开**。——这一条我们承诺了、没做到。
3. **输入区域（PUT）**：fuzz 给出一个值；我们承诺给出**一个被证明的输入区间**，
   让测试变成参数化的、带断言的。——**这是唯一无可替代的东西，而它现在是 0。**

⇒ **我们放弃了唯一的护城河（第 3 条），去和 fuzz 拼它最强的地方（第 1 条的实现细节）。**

### 4.3 更刺耳的一条

我们**本可以直接用 fuzz 当作 stage-1**：让 forge fuzz 去找具体输入（它擅长），
我们只做 stage-2/3（把那个具体输入长成被证明的区间 + 断言）。那样 X→Y 这一格
根本不是问题，而我们全部的力气会花在**只有我们能做的那一格**上。

**我五天里一次都没考虑过这个方案。** 我默认了"路径必须由我们的符号执行来见证"，
而这个默认从来没有被论证过。

## 8. 补救方案（具体到可执行，按优先级）

### P0 — 让 B 从 0 变成 1（不到一天）

**目标**：一个合约、一条路径、一个带 `vm.assume(lo <= x && x <= hi)` 和一条
post-state 断言的 `.t.sol`，`forge test` 跑绿。**允许手工补任何一环。**

理由：链上有四个环节（枚举、区域、断言、渲染），现在**没有任何一条链是通的**，
所以"哪一环真的缺"全是推测。一条通的链会把推测变成事实。

现成材料：`regression/R0.cov.t.sol` 已存在；aqua 有 12 个**真正有宽度**的坐标。
**从 aqua 的那 12 个坐标里挑一个。**

### P1 — 具体部署（这是 §3 的修法，也是 st1inch 0/86 的修法）

**做法**：给 harness 一个模式，构造器参数取**具体值**（来自配置或一次预跑），
构造器**具体执行**（或其守卫被简化器以闭公式判真），单元体仍然符号执行。

**判别器（先写，后改）**：在 D36 的 `r4_vpcalls` 那一格上，
- 现在：`F 0, U 4`
